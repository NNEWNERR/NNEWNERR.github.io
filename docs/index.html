สาย Automation QA ทำอะไร และต้องมีอะไร

งาน QA ไม่ใช่การหาบั๊กให้ได้เยอะที่สุด แต่เป็นการให้ข้อมูลที่ทีมเชื่อได้ ว่าของที่จะปล่อยออกไปมีความเสี่ยงตรงไหน และเสี่ยงแค่ไหน บั๊กที่เจอเป็นผลพลอยได้ ส่วนสิ่งที่ทีมต้องการจริงคือ "กล้าปล่อย" หรือ "ยังไม่ควรปล่อย" พร้อมเหตุผล

Manual QA, Automation QA และ SDET ต่างกันยังไง

บทบาทงานหลักสิ่งที่ส่งมอบ
Manual QAออกแบบ test case แล้วทดสอบด้วยมือ สำรวจระบบหาจุดที่ spec ไม่ได้พูดถึงtest case, รายงานบั๊ก, ผลทดสอบก่อนปล่อย
Automation QAเปลี่ยน test case ที่ต้องรันซ้ำให้เป็นโค้ด แล้วต่อเข้า CI ให้รันเองทุกครั้งที่โค้ดเปลี่ยนชุดเทสที่ทีมดูแลต่อได้ และรายงานที่อ่านแล้วรู้ทันทีว่าพังตรงไหน
SDETสร้างเครื่องมือและโครงสร้างให้ทั้งทีมเขียนเทสได้ง่าย เช่น test data, fixture, environment, pipelineframework, เครื่องมือ, มาตรฐานการเทสของทีม

สามบทบาทนี้ไม่ได้แยกขาดกัน Automation QA ที่ดียังต้องออกแบบเทสเป็นแบบ manual QA เพราะโค้ดเทสที่ดีมาจากเทสที่ออกแบบดี ถ้าเอาเทสที่ออกแบบไม่ดีมาเขียนเป็นโค้ด ก็ได้แค่เทสไม่ดีที่รันเร็วขึ้น

ทักษะที่ใช้จริงทุกวัน

  • ออกแบบเทส: ตอบได้ว่าทำไมต้องเทสค่านี้ ทำไมไม่ต้องเทสค่านั้น ดูเทคนิคออกแบบเทส
  • เขียนโค้ด: TypeScript หรือภาษาที่ทีมใช้ ระดับที่เขียน Page Object, fixture และ helper ที่คนอื่นอ่านรู้เรื่อง
  • เข้าใจระบบที่เทส: HTTP, การล็อกอินและ session, ฐานข้อมูล, สิทธิ์การเข้าถึง เพราะบั๊กที่แพงที่สุดมักอยู่ใต้หน้าจอ ไม่ใช่บนหน้าจอ
  • CI: ให้เทสรันเองทุกครั้งที่โค้ดเปลี่ยน และอ่าน log ได้เมื่อมันพัง
  • สื่อสาร: รายงานบั๊กที่ developer เปิดอ่านแล้วทำซ้ำได้ในครั้งเดียว และบอกคนที่ไม่ใช่สายเทคนิคได้ว่าความเสี่ยงคืออะไร
  • คิดเชิงความเสี่ยง: เวลามีจำกัดเสมอ ต้องเลือกเทสสิ่งที่ถ้าพังแล้วเสียหายมากที่สุดก่อน

เทสหลายชั้น ไม่ใช่ E2E อย่างเดียว

unit→API / rules→UI (E2E)→ทดสอบกับ production

ยิ่งขยับไปทางขวา เทสยิ่งใกล้สิ่งที่ผู้ใช้เจอ แต่ก็ยิ่งช้าและพังง่ายขึ้นด้วย ตัวอย่างจาก repo ของผม: multitenant-booking-qa ใช้ rules test 76 เคสพิสูจน์เรื่องสิทธิ์ ซึ่งรันเร็วและนิ่ง แล้วใช้ UI test แค่ 17 เคสกับสิ่งที่ชั้นล่างมองไม่เห็น เช่นปุ่มที่กดไม่ได้บนมือถือ เลือกชั้นให้ถูกตั้งแต่ต้นสำคัญกว่าจำนวนเทส

วัดคุณภาพชุดเทสด้วยอะไร

  • จับบั๊กได้จริงไหม: ลองย้อนโค้ดกลับเป็นรุ่นที่มีบั๊ก ชุดเทสต้องแดง (ดู mutation check ในหัวข้อ security rules)
  • จอแดงหมายถึงบั๊กจริงไหม: ถ้าแดงเพราะเทสไม่นิ่งบ่อยๆ ทีมจะเลิกเชื่อ ดูFlake playbook
  • รู้ผลเร็วแค่ไหน: เทสที่รู้ผลหลัง merge ไปแล้วสามวัน ช่วยได้น้อยกว่าเทสที่ฟ้องตั้งแต่ตอนเปิด PR

จำนวนเทสบอกได้แค่ว่าเขียนไปเยอะ ไม่ได้บอกว่าปลอดภัย

ถ้าจะเริ่ม: ลำดับที่ผมเดินมา

  1. เรียนเทคนิคออกแบบเทสก่อนเครื่องมือ เพราะใช้ได้กับทุกเครื่องมือ
  2. เขียน Playwright กับระบบ demo สาธารณะ เช่น sauce-demo-tests ฝึก Page Object, locator และ assertion ให้แน่น
  3. ต่อ CI ให้รันเองทุก push แล้วเริ่มเจอปัญหาที่เครื่องตัวเองไม่เคยเจอ เช่นฟอนต์ต่างกันระหว่าง OS ใน visual test
  4. สร้างระบบเล็กๆ ของตัวเองแล้วเทสทุกชั้น อย่าง multitenant-booking-qa จะทำเรื่องที่ demo ทำไม่ได้ เช่น seed ข้อมูลและสลับ role
  5. ทดสอบระบบจริงที่มีผู้ใช้ ที่นี่จะได้เรียนเรื่องที่ไม่มีในหนังสือ เช่นข้อมูลรุ่นเก่า ความเสี่ยงของการเทสบน production และการไล่บั๊กที่เกิดแค่บางครั้ง (ดู case studies)

ผมเริ่มจากการเป็น frontend developer อยู่ 1 ปี ซึ่งช่วยมากในข้อ 4 และ 5 เพราะอ่านโค้ดของระบบที่เทสได้ แต่ไม่จำเป็นต้องเริ่มจากตรงนั้น สายนี้เติบโตต่อไปเป็น SDET หรือ QA Lead ได้ ซึ่งเป็นทางที่ผมกำลังไป

ระบบที่ผมทดสอบ

เทสจะมีความหมายก็ต่อเมื่อรู้ว่าระบบทำอะไร ใครใช้ และถ้าพังจะเสียอะไร หัวข้อนี้อธิบายระบบเบื้องหลังผลงานทั้ง 4 ชิ้นบนหน้าแรก เรียงจากระบบจริงไปจนถึงระบบตัวอย่าง

Krungthon Air: ระบบจองคิวช่างแอร์ที่ใช้งานจริง

ระบบคืออะไรเว็บจองคิวบริการแอร์ ลูกค้าจองวันและเวลาเองผ่านหน้าเว็บหรือ QR ของแต่ละสาขา พนักงานจัดตารางช่าง แล้วระบบแจ้งเตือนผ่าน LINE และ Discord รองรับหลายร้านในระบบเดียว (multi-tenant)
ใครใช้ลูกค้าที่จองโดยไม่ต้องมีบัญชี และฝั่งหลังบ้าน 5 role: พนักงาน, เจ้าหน้าที่ประกัน, แอดมิน, แอดมินของร้าน และแอดมินของแพลตฟอร์ม
เทคโนโลยีAngular, Firebase (Firestore, Auth, Cloud Functions), LINE OA
ถ้าพังจะเสียอะไรคิวช่างชนกัน, ลูกค้าจองไม่ได้แล้วไปร้านอื่น, ข้อมูลลูกค้า (ชื่อ เบอร์ ที่อยู่) รั่วไปร้านอื่นหรือคนที่ไม่ได้ล็อกอิน
ทดสอบตรงไหนE2E/API 96 เทสในเส้นทางจอง ตารางช่าง สิทธิ์ของแต่ละ role และการจองชนกัน, rules 90 เทสสำหรับสิทธิ์ในฐานข้อมูล และ daily soak ที่ยิงกับ production ทุกวัน (จำนวนจาก repo ณ 2026-10-16)

เป็นระบบของลูกค้า โค้ดและข้อมูลจึงเปิดไม่ได้ สิ่งที่เล่าได้คือวิธีคิด ซึ่งอยู่ใน case studies ทั้ง 8 เคส

multitenant-booking-qa: ระบบจองที่ผมสร้างเองเพื่อเทสทุกชั้น

ระบบคืออะไรแอปจองขนาดเล็ก (Booking Desk) ที่หลายองค์กรใช้ฐานข้อมูลเดียวกัน ทุกเอกสารมีรหัสองค์กรเจ้าของกำกับ ผมสร้างขึ้นใหม่ทั้งหมดจากโจทย์แบบเดียวกับระบบจริง โดยไม่ใช้โค้ดหรือข้อมูลของลูกค้า
ใครใช้4 role: admin, staff, customer และ platform_admin
ทำไมต้องสร้างเองเทสกับ demo ของคนอื่นทำได้แค่คลิกตาม แต่ระบบที่เป็นเจ้าของเองทำให้ seed ข้อมูลรุ่นเก่า สลับ role และพิสูจน์สิ่งที่ต้องถูกปฏิเสธได้
ถ้าพังจะเสียอะไรองค์กรหนึ่งเห็นหรือแก้การจองขององค์กรอื่นได้ ซึ่งการจองมีชื่อ เบอร์ และที่อยู่ลูกค้า
ทดสอบตรงไหนrules 76 เทส (แยกองค์กร, สิทธิ์ตาม role, การเปลี่ยนสถานะ, ข้อมูลรุ่นเก่า, ขอบเขตของคนที่ยังไม่มีสังกัด) และ UI 17 เทสบนเดสก์ท็อปกับ Pixel 7

qa-automation: ชุดเทสหลายชั้นบนระบบ demo สาธารณะ

ระบบคืออะไรระบบ demo สาธารณะ 2 ตัว: JSONPlaceholder (API ปลอมสำหรับฝึก) และ TodoMVC (แอปรายการสิ่งที่ต้องทำ)
ทำไมเลือกใครก็ clone แล้วรันได้ทันทีโดยไม่ต้องมีบัญชี จึงเหมาะกับการโชว์เทคนิคที่หลากหลาย: API contract, UI, accessibility, visual regression และ auth แยก role
จุดที่ต่างจาก demo ทั่วไปCI แบ่งรัน 4 shard แล้วรวมเป็นรายงานเดียว และมีการทดลองใช้ AI agent เขียนเทสภายใต้กติกา พร้อมบันทึกผลรอบแรกตามจริง (ดูหัวข้อ Test Agents)

sauce-demo-tests: ร้านค้าออนไลน์ตัวอย่าง

ระบบคืออะไรSauce Demo ร้านค้าออนไลน์จำลองที่ทำไว้ให้ฝึกเทส มี login, รายการสินค้า, ตะกร้า และ checkout
ทำไมเลือกเป็นเส้นทางซื้อของที่ทุกคนเข้าใจ จึงเหมาะกับการโชว์พื้นฐานให้แน่น: Page Object 4 หน้า, เทส accessibility และเอกสารกลยุทธ์การทดสอบ (TESTING.md) ที่บอกว่าเลือกเทสอะไรเพราะอะไร

เทคนิคออกแบบเทส

เทสที่ดีตอบได้ว่า "ทำไมต้องเป็นค่านี้" ทุกตัว ถ้าตอบไม่ได้ มักเป็นการไล่คลิกแล้วบันทึกไว้ ซึ่งได้จำนวนเทสเยอะแต่จับบั๊กได้น้อย สี่เทคนิคนี้ใช้บ่อยที่สุดในงานของผม

Equivalence partitioning: ค่าในกลุ่มเดียวกันให้ผลเหมือนกัน ทดสอบตัวแทนตัวเดียวพอ

แบ่ง input เป็นกลุ่มที่ระบบควรปฏิบัติเหมือนกัน แล้วเลือกตัวแทนกลุ่มละหนึ่งค่า ประหยัดเทสโดยไม่เสียความครอบคลุม

ตัวอย่างจริง: ใน qa-automation เทส GET /posts?userId=1 ใช้ user คนเดียวแทน user ทุกคน เพราะ user ที่มีอยู่ทุกคนอยู่กลุ่มเดียวกัน แต่ user ที่ไม่มีอยู่เป็นอีกกลุ่ม ซึ่งต้องมีเทสของตัวเอง

Boundary value analysis: บั๊กชอบอยู่ที่ขอบ

เมื่อมีช่วงหรือเงื่อนไขเปลี่ยน ให้ทดสอบที่ค่าขอบและค่าติดขอบ เช่น 0, 1, 2 หรือ max, max+1

ตัวอย่างจริง: ตัวนับของ TodoMVC เปลี่ยนรูปประโยคระหว่าง 1 item left กับ 2 items left เทสใน todo.spec.ts จึงตั้งใจครอบทั้งกรณี 1 รายการและหลายรายการ ส่วนกรณี 0 รายการ (footer ต้องหายไป) อยู่ในเทสชุด generated

Decision table: เมื่อผลลัพธ์ขึ้นกับหลายเงื่อนไขพร้อมกัน

เขียนตารางให้ครบทุกคู่ของเงื่อนไข แล้วใส่ผลที่ควรเกิดในแต่ละช่อง ช่องที่เขียนผลไม่ออกคือช่องที่ spec ยังไม่ได้ตัดสินใจ ซึ่งมักเป็นที่ซ่อนของบั๊ก

role \ หน้าจอรายการจองอนุมัติตั้งค่าองค์กร
adminเห็นทั้งองค์กรได้ได้
staffเห็นทั้งองค์กรได้ไม่ได้
memberเห็นของตัวเองไม่ได้ไม่ได้
role ใหม่???

ตารางนี้เป็นรูปแบบที่ใช้ใน CS-02 ตอนเพิ่ม role ใหม่หนึ่งตัวแล้วพังเงียบ 6 จุด แถวที่มีแต่ "?" คือสิ่งที่ต้องถามทีมก่อนเขียนเทส

State transition: ไล่ทุกเส้น โดยเฉพาะเส้นย้อนกลับ

วาดสถานะกับเส้นที่เปลี่ยนสถานะได้ แล้วทดสอบทุกเส้น คนส่วนใหญ่ทดสอบแค่เส้นตรงไปข้างหน้า

สร้างงาน→จองที่ในตาราง→ยกเลิก→ที่นั่งต้องถูกคืน→จองใหม่ช่วงเดิมได้

ตัวอย่างจริง: CS-03 เส้น "สร้าง → ยกเลิก → จองใหม่" ไม่มีใครเคยไล่ ผลคือที่นั่งค้างอยู่ 640 รายการ ส่วนในเทสชุด generated ของ TodoMVC มี "กด toggle-all สองครั้งต้องกลับเป็น active ทั้งหมด" ซึ่งก็เป็นเส้นย้อนกลับเหมือนกัน

Flake playbook

เทสที่ผ่านบ้างไม่ผ่านบ้างอันตรายกว่าเทสที่แดงตลอด เพราะสอนให้ทีมเลิกเชื่อสีแดง กติกาข้างล่างนี้ใช้ทุก repo

1. ใช้ web-first assertion ห้ามรอด้วยเวลา

✗ ไม่ทำ
await page.waitForTimeout(2000)
expect(await items.count()).toBe(3)
✓ ทำ
await expect(items).toHaveCount(3)

expect(locator) retry ให้เองจนกว่าจะจริงหรือหมดเวลา ส่วน waitForTimeout เดาเวลา ซึ่งช้าเกินบนเครื่องเร็วและสั้นเกินบน CI ที่โหลดหนัก networkidle ก็เข้าข่ายเดียวกัน

2. ลำดับการเลือก locator

getByRole → getByLabel → getByPlaceholder → getByText → getByTestId → CSS เป็นทางสุดท้าย ถ้าจำเป็นต้องใช้ CSS ให้เขียนเหตุผลไว้ เช่นตัวนับ .todo-count ของ TodoMVC ที่ไม่มี role หรือ label ให้จับ

3. กับดักที่เจอจริง: assertion ที่จับภาพครั้งเดียว

✗ จับภาพครั้งเดียว ไม่ retry
for (const item of await items.all()) {
  await expect(item).toHaveClass(/completed/)
}
✓ retry ทั้งรายการ
await expect(items).toHaveClass(
  [/completed/, /completed/, /completed/])

4. กับดักที่เจอจริง: uncheck() บนแถวที่หายไปหลังคลิก

check()/uncheck() คลิกแล้วตรวจซ้ำว่าสถานะเปลี่ยน ถ้าแถวนั้นหายไปจากหน้าทันทีหลังคลิก เช่นอยู่ในตัวกรอง Completed แล้วเอาเครื่องหมายออก การตรวจซ้ำจะรอ element ที่ไม่มีอยู่แล้วจน timeout ทางแก้คือใช้ click() แล้ว assert ผลลัพธ์ที่ตัวรายการแทน

5. กับดักที่เจอจริง: addInitScript รันซ้ำตอน reload

fixture ที่ล้าง localStorage ด้วย init script จะล้างซ้ำทุกครั้งที่โหลดหน้า รวมถึง page.reload() ทำให้เทส "ข้อมูลอยู่หลัง reload" ไม่มีทางผ่าน ทางแก้คือใส่ flag ใน sessionStorage ซึ่งอยู่รอดหลัง reload แต่ไม่ข้ามไปเทสถัดไป

await page.addInitScript(() => {
  if (sessionStorage.getItem('qa:storage-cleared')) return
  localStorage.clear()
  sessionStorage.setItem('qa:storage-cleared', '1')
})

6. Retry: บันทึกไว้ ไม่ใช้กลบ

  • flake จากระบบภายนอก เช่น JSONPlaceholder ช้าตอนโหลดหนัก ให้บันทึกใน README พร้อมอาการและความถี่
  • ไม่เพิ่ม retry ในเครื่องเพื่อให้เขียว เพราะ retry ตัวเดียวกันจะกลบบั๊กจริงในเทสนั้นด้วย
  • dependency ที่ไม่พร้อม เช่นแอป local ที่ไม่ได้เปิด ให้ skip พร้อมข้อความ ไม่ใช่ fail

ทดสอบ Firestore security rules

security rules คือด่านเดียวระหว่างผู้ใช้กับฐานข้อมูล การทดสอบว่า "ทำได้" ยังไม่พอ ต้องพิสูจน์ว่าสิ่งที่ต้องถูกปฏิเสธถูกปฏิเสธจริง

หลักที่ใช้ใน multitenant-booking-qa (76 เคส)

  • รันกับ emulator จริง ไม่ใช้ mock: rules ที่ mock ไว้จะผ่านเสมอ แม้ rules จริงจะผิด
  • เทสฝั่งปฏิเสธเยอะกว่าฝั่งอนุญาต: ข้าม tenant, role ไม่พอ, ยังไม่มีสังกัด, ไม่ล็อกอิน
  • seed ข้อมูลรุ่นเก่า (legacy shape): เอกสารที่สร้างก่อนเปลี่ยน schema มักหลุดเงื่อนไขของ rules ใหม่
  • ตั้งชื่อเส้นแบ่งให้ถูก: ชุด public-boundary พิสูจน์ว่าเส้นแบ่งสิทธิ์คือ "ยังไม่มีสังกัด" ไม่ใช่ "ยังไม่ล็อกอิน" สองอย่างนี้ฟังเหมือนกันแต่ให้ผลต่างกัน

จาก tests/tenant-isolation.test.ts (ย่อ): ออกแบบเป็น decision table: ผู้กระทำ × เจ้าของเอกสาร × operation

beforeEach(async () => {
  const env = await getTestEnv()
  await env.clearFirestore()
  await seed(env, 'bookings/bkA', { tenantId: TENANT_A, status: 'pending', customerId: 'custA' })
  await seed(env, 'bookings/bkB', { tenantId: TENANT_B, status: 'pending', customerId: 'custB' })
})

test('staff reads a booking in their own tenant', async () => {
  const db = user(await getTestEnv(), 'uA', TENANT_A, 'staff').firestore()
  await assertSucceeds(getDoc(doc(db, 'bookings/bkA')))
})

test('tenant B staff cannot READ a tenant A booking', async () => {
  const db = user(await getTestEnv(), 'uB', TENANT_B, 'staff').firestore()
  await assertFails(getDoc(doc(db, 'bookings/bkA')))

Mutation check: ถ้าย้อน rules กลับเป็นของเก่า เทสต้องแดง

Playwright Test Agents: ใช้ AI เขียนเทสแบบมีรั้ว

planner→specs/*.md (แผน = oracle)→generator→tests/generated/→healer

Playwright มี agent สามตัวที่ใช้ร่วมกับ Claude Code ได้ ค่าเริ่มต้นของ healer ถูกสั่งให้ "ทำทุกอย่างที่สมเหตุสมผลให้เทสผ่าน" ซึ่งเหมาะกับ demo แต่อันตรายกับชุด regression เพราะเทสที่แก้ assertion ตัวเองจะเขียวในจังหวะที่ควรจับบั๊กพอดี

รั้วที่ใส่ไว้ใน qa-automation

  • healer แก้ locator ได้ แต่ห้ามแก้ค่าที่คาดหวัง ห้ามลด assertion และห้ามเพิ่ม retry หรือ timeout
  • แผนใน specs/ คือ oracle ถ้าแอปไม่ตรงแผน ให้ทำ test.fixme แล้วรายงาน ไม่ใช่ปรับเทสให้ตรงกับแอป
  • แก้ได้เฉพาะใต้ tests/generated/
