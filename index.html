Case studies — บั๊กจริงจากระบบที่ใช้งานอยู่

โค้ดของระบบลูกค้าเอามาแสดงไม่ได้ แต่วิธีคิดตอนไล่หาสาเหตุเล่าได้ ทุกเคสเรียงตามลำดับเดียวกัน: อาการ → ตามรอย → สาเหตุราก → แก้ → ยืนยัน → บทเรียน

CS-01

login ล้มแบบสุ่ม 1 ใน N ครั้ง — race condition ระหว่าง session สองเส้น

แยกให้ออกว่า "เทสไม่นิ่ง" หรือ "ระบบไม่นิ่ง" ก่อนใส่ retry

 CS-02

เพิ่ม role ใหม่ 1 ตัว พังเงียบ 6 จุด

decision table (role × หน้าจอ), เคส refresh / deep link

 CS-03

คิวเต็มทั้งที่งานยกเลิกแล้ว — ที่นั่งค้าง 640 รายการ

state-transition testing, remediation แบบ idempotent

 CS-04

กันข้อมูลข้ามองค์กรรั่ว — ทดสอบ 3 ชั้น เจอบั๊กครบ 3 ชั้น

negative testing, rules test บน emulator (91 เคส), defense in depth

 CS-05

deploy แล้วบางเครื่องเห็นหน้าเก่า — service worker ที่ตายไม่ลง

แยกตัวแปรด้วย incognito, ยืนยันที่ HTTP header

 CS-06

ปุ่มที่ "มองเห็น" แต่ "กดไม่ได้" และเกิดเฉพาะบนมือถือ

hit-testing แทน visibility, ทดสอบแยกตามขนาดจอ

 CS-07

สิทธิ์ของระบบรุ่นเก่าที่ลืมปิด — คนไม่ล็อกอินอ่านข้อมูลลูกค้าได้ทั้งหมด

security rules review, mutation check (กฎเดิมแดง 15 เคส), blast radius

 CS-08

เทสฟ้องว่า "จองซ้อนได้" ทั้งที่ระบบถูก — บั๊กของเทส 4 ชั้น

ยิง API ตรงแยกระบบออกจากเทส, event-driven assertion, test-data isolation

สิ่งที่ผมให้ความสำคัญมากกว่าจำนวนเทส

จอแดงต้องหมายถึงบั๊กจริงเสมอ ถ้าทีมเริ่มชินกับการเห็นแดง ชุดเทสก็หมดค่า

Skip แทน fail เมื่อ dependency ไม่พร้อม

เทสที่ล้มเพราะสภาพแวดล้อมกับเทสที่ล้มเพราะบั๊ก หน้าตาในรายงานเหมือนกัน การ skip พร้อมเหตุผลทำให้แยกสองอย่างนี้ออกจากกันได้

Flake จากระบบภายนอก บันทึกไว้ ไม่กลบด้วย retry

retry ที่ใส่เพื่อให้ผ่าน จะบังบั๊กจริงที่เกิดในเทสตัวเดียวกันด้วย

Screenshot baseline ผูกกับ OS เสมอ

เพราะการ render ฟอนต์ต่างกันจริง baseline ที่สร้างใหม่ตัวเองทุก push ทำให้ visual regression ไม่มีความหมาย

เส้นที่ร้อยทุก case study

  • บั๊กที่ "เจอบ้างไม่เจอบ้าง" คือบั๊กที่ต้องสืบ ไม่ใช่บั๊กที่ต้องกลบ CS-01
  • เส้นทางย้อนกลับ (ยกเลิก / ปฏิเสธ / refresh) คือที่ที่บั๊กชอบอยู่ CS-02 · CS-03
  • ยืนยันด้วยสิ่งที่วัดได้ ไม่ใช่ด้วยสายตา — header, ตัวที่รับคลิกจริง, ผลลัพธ์ที่ต้องถูกปฏิเสธ CS-04 · CS-05 · CS-06
  • "ผ่าน" ของเครื่องมือ ไม่เท่ากับ "ใช้งานได้" ของผู้ใช้ CS-06
  • เทสที่ฟ้องบั๊กร้ายแรง ต้องพิสูจน์ที่ระบบก่อน CS-08
